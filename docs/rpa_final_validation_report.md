ingestion pipeline, reconciliation against an independent Excel oracle, relationship
coverage, implemented metrics, API surface, and test/lint/typecheck/build results
for the four dashboards (Executive, Operations, ROI, SLA/Service Performance).

## 3. Source reconciliation (independent Excel oracle)

`backend/tests/oracle/excel_oracle.py` reads the workbook directly with
`openpyxl` and imports nothing from `app.*` — no ingestion module, no service,
no repository. `backend/tests/integration/test_excel_reconciliation.py`
ingests the real workbook once (module-scoped) and reconciles PostgreSQL
results against the oracle. **All 11 reconciliation tests pass**, covering
every item in the brief's "at minimum reconcile" list:

- Raw ticket count (712) vs. distinct ticket count (709, after excluding the
  1 blank-`TICKET_ID` row and collapsing 2 duplicate `TICKET_ID`s)
- Open (38) / closed (671) tickets
- L1 (642) / L2 (67) tickets
- Annual saving (`bc_saving × Σ fte_hours_month_actual × 12`)
- AMS 1L cost total, AMS 2L cost total (referential-integrity-scoped to
  known tickets, matching core's own exclusion rule)
- License cost by year (exact per-year totals)
- Company / process / root-cause ticket totals
- Resolution-day statistics (avg, closed-with-dates count)

**A genuine bug was found and fixed via this reconciliation**: one `TICKETS`
row uses a dash-separated date (`20-05-2026`) instead of the source's
otherwise-consistent slash format (`DD/MM/YYYY`). The date parser
(`app/ingestion/normalization.py::normalize_date_european`) silently failed
to parse it, turning a **closed** ticket into an apparently **open** one. Fixed
by accepting both `%d/%m/%Y` and `%d-%m-%Y` (plus their datetime variants),
with a regression test (`test_normalize_date_european_accepts_dash_separators`).

## 6. Implemented vs. unavailable metrics

All metrics listed in the brief's METRICS section are implemented across the
four services (`app/services/{executive,operations,roi,service_performance}.py`),
each returned as a typed `MetricValue` envelope
(`metric_name, value, unit, available, status, period, filters, warnings, calculated_at`).

**Deliberately unavailable, not fabricated zero**, per the SHARED COSTS rule:

- `kpi_run_cost_3y_eur`, `kpi_tco_3y_eur`, `kpi_net_benefit_3y_eur`,
  `kpi_roi_3y_full_cost_pct` / `roi_run_cost_3y_eur` etc. become `available: false`
  the moment a **company** filter is applied on the Executive page — AMS 1L
  and license costs are portfolio-level with no documented per-company
  allocation rule, so attributing the full portfolio run cost to one company
  would misrepresent it.
- Every row in `GET /api/v1/roi/processes` and `/roi/quick-wins` carries
  `process_tco_available: false` — CAPEX is legitimately per-process
  (from `ECONOMICS`), but AMS 1L/license costs have no per-process
  allocation rule, so a full process-level TCO is never invented.
- Any KPI dependent on `resolution_stats` (avg/median/P90 resolution, SLA
  proxy) returns `available: false` when there are zero closed tickets with
  valid dates, instead of `0`.

## 11. Known limitations

- **Staged/audited but not modeled as core entities**: `TCO` (real SAP PO
  ledger — overlaps with the dedicated AMS 1L/2L/LICENSES sheets and has a
  genuine column-shift defect in early rows; not part of the required core
  entity list), `AMS RFC`, `AMS SMS` (freeform, inconsistent row shapes),
  `TICKETS_OUT` (unrelated IT helpdesk log, no process/root-cause linkage).
  All rows are staged and auditable; none feed core tables or KPIs.
- **PII**: `TICKETS.REQUESTOR` and free-text `NOTE` fields are retained in
  `staging`/`core` for audit traceability but are never exposed via any API
  response schema.
- **Shared costs**: AMS 1L and license costs have no documented per-process
  or per-company allocation rule; every metric that would require inventing
  one is marked `available: false` rather than estimated.
- **Chart interaction depth**: charts follow the dataviz skill's palette,
  mark, and legend rules, but do not implement full crosshair/tooltip
  interaction depth, dark-mode re-theming, or CVD texture fills, given the
  scope of this build.
- **Pre-existing scaffold defects fixed as a side effect of this work**
  (unrelated to the RPA domain, but blocking `make test-all`): `tsconfig.node.json`
  missing `noEmit` under `composite: true`; `vite.config.ts`'s merged Vitest
  `test` config field needing `/// <reference types="vitest/config" />`;
  `index.css` referencing a non-existent Tailwind class `font-inherit`;
  `vitest@2.1.8` bundling a `vite@5` dependency that duplicate-installed
  alongside the pinned `vite@6.0.6` (bumped to `vitest@3.2.7`, which supports
  Vite 6 and dedupes cleanly).
- Frontend production bundle is ~649KB gzipped ~194KB (Recharts is the
  largest contributor); a chunk-size warning is emitted but the build
  succeeds. Code-splitting is a reasonable future optimization, not required
  for correctness.
